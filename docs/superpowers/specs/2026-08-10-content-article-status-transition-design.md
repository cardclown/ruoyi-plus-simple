# 文章发布与撤回接口设计

## 背景

当前文章模块只能通过完整修改接口变更发布状态。该接口要求前端同时提交标题、正文、分类等必填字段，并会重建标签关系，不适合列表页的独立“发布/撤回”操作。

本次新增一个只接收文章 ID 和目标状态的状态接口，同时约束已发布文章的普通编辑流程。

## 目标

- 支持列表页仅传 `articleId` 和 `status` 完成发布或撤回。
- 所有状态操作都受租户边界和文章数据权限约束。
- 状态接口只更新状态、发布审计字段和更新审计字段，不修改文章内容或标签。
- 已发布文章必须先撤回为草稿，才能继续普通编辑或再次发布。
- 使用独立的状态请求对象，使接口契约与普通文章编辑彻底分离。

## 非目标

- 不新增菜单或按钮权限记录。
- 不修改文章表结构或数据库脚本。
- 不引入审核流程、定时发布、版本历史或发布记录表。
- 不在本次后端改动中实现前端按钮。

## 方案选择

### 采用方案：新增 `ContentArticleStatusBo`

新增一个只包含 `articleId` 和 `status` 的 `ContentArticleStatusBo`。两个字段在该 BO 内直接声明必填和状态格式校验，控制器不需要额外的 JSON View 或校验分组。

该方案使状态修改契约可以独立阅读、验证和演进，也避免在通用 `ContentArticleBo` 内继续叠加视图与校验分组。`ContentArticleStatusBo` 不继承 `BaseEntity`，不暴露审计字段或 `params`。

### 未采用方案

- 复用 `ContentArticleBo` 并新增 `StatusView/StatusGroup`：可以少一个类，但会把状态契约继续叠加到普通编辑 BO 中，降低可读性。
- 使用 URL 查询参数：实现简单，但与项目内其他状态修改接口的 JSON 请求风格不一致。

## HTTP 接口契约

### 请求

```http
POST /content/article/changeStatus
Content-Type: application/json
```

```json
{
  "articleId": 2085567048592797698,
  "status": "1"
}
```

字段约束：

- `articleId`：必填，用于定位文章。
- `status`：必填，只允许字符串 `"0"` 或 `"1"`。
- 请求中的其他文章字段不进入状态操作的绑定结果。

### 权限和日志

- 复用 `content:article:edit` 权限，不新增菜单 SQL。
- 记录文章更新操作日志。
- 使用重复提交防护。

### 响应和错误

- 更新成功返回框架统一的成功响应。
- ID 为空或状态不是 `0/1` 时，由参数校验返回明确错误。
- 文章不存在或超出当前数据权限时，返回“文章不存在或无权操作”。
- 已发布文章再次请求发布时，返回“文章已发布，请先撤回后再发布”。
- 底层更新影响行数不是 1 时，返回“文章状态修改失败”。

## 状态机

| 数据库当前状态 | 目标状态 | 处理 |
|---|---|---|
| 草稿 `0` | 草稿 `0` | 允许，按无状态变化处理 |
| 草稿 `0` | 发布 `1` | 允许，写入当前操作人和当前时间作为发布信息 |
| 发布 `1` | 草稿 `0` | 允许，清空发布人和发布时间 |
| 发布 `1` | 发布 `1` | 拒绝，必须先撤回为草稿 |

对于状态接口的 `0 -> 0`，服务可直接返回成功，不执行无意义的数据库更新。

## 普通修改接口约束

现有 `PUT /content/article` 保留“保存并发布”能力，但增加对数据库当前状态的约束：

- 当前为草稿 `0`，请求状态为 `0`：允许反复修改草稿。
- 当前为草稿 `0`，请求状态为 `1`：允许保存全部修改并发布。
- 当前为已发布 `1`：无论请求状态为 `0` 还是 `1`，普通修改都拒绝，提示“已发布文章请先撤回为草稿后再修改”。

撤回必须通过独立状态接口完成，避免普通修改在一次请求中同时撤回和改写已发布内容。

## 服务层流程

### 状态修改

1. 服务层再次校验目标状态只能为 `0/1`。
2. 通过带数据权限的 Mapper 方法读取当前文章。
3. 文章不存在或不可见时终止操作。
4. 按状态机校验转换是否允许。
5. `0 -> 0` 直接返回成功。
6. 对 `0 -> 1` 写入发布人和发布时间，对 `1 -> 0` 清空发布信息。
7. 使用受数据权限约束的局部更新 Mapper 方法写入数据。

### 普通修改

在读取持久化文章之后、准备新文章和删除旧标签之前，先检查持久化状态。如果当前已发布，立即抛出业务异常，确保文章和标签都不会被修改。

## 持久化边界

不能直接对部分填充的 `ContentArticle` 调用现有完整 `updateById`，因为 `tagIds`、`coverOssId`、`publishBy` 和 `publishTime` 含有 `FieldStrategy.ALWAYS`，部分实体更新可能将无关字段置空。

需新增一个受 `@DataPermission` 约束的 Mapper 局部更新方法，明确只设置：

- `status`
- `publish_by`
- `publish_time`
- `update_by`
- `update_time`

租户插件继续约束租户边界，`@DataPermission` 继续约束 `create_dept/create_by` 数据权限。局部更新不触碰标题、正文、分类、封面、标签或删除标志。

## 测试设计

### 控制器契约

- 路径为 `POST /content/article/changeStatus`。
- 权限为 `content:article:edit`。
- 具备更新日志和重复提交防护。
- 使用 `ContentArticleStatusBo` 作为唯一请求体。

### 请求对象

- `ContentArticleStatusBo` 只声明 `articleId` 和 `status`，不继承通用实体基类。
- 请求中即使出现其他文章字段，也不会进入状态业务对象。
- ID 缺失、状态缺失、状态非 `0/1` 均校验失败。

### 服务层

- `0 -> 0` 成功且不执行更新。
- `0 -> 1` 写入当前发布人和时间。
- `1 -> 0` 清空发布人和时间。
- `1 -> 1` 拒绝。
- 非法状态在服务层被防御性拒绝。
- 文章不存在或无数据权限时拒绝。
- 已发布文章不能调用普通修改。
- 草稿可以继续保存为草稿，也可以保存并发布。
- 状态修改不调用标签删除或新增方法。

### Mapper 契约

- 局部更新方法具备 `@DataPermission`。
- 更新语句只包含状态、发布审计和更新审计字段。

## 预计修改范围

- `ContentArticleStatusBo`：新增只包含文章 ID 和目标状态的专用请求对象。
- `ContentArticleController`：新增 `POST /changeStatus`。
- `IContentArticleService` 及 `ContentArticleServiceImpl`：状态修改流程与已发布文章的普通编辑限制。
- `ContentArticleMapper`：受数据权限约束的局部状态更新。
- 新增状态 BO 校验测试，并修改现有控制器、Service 和 Mapper 契约测试：先失败，再用最小代码使其通过。

## 验收标准

- 前端仅提交 ID 和状态即可发布或撤回。
- 状态转换和普通编辑限制符合本文档状态机。
- 局部状态更新不改变标签、封面或文章内容。
- 数据权限、租户隔离、审计字段和发布字段处理正确。
- 新增回归测试与 `ruoyi-content` 模块全量测试通过。
